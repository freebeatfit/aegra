title: "Streaming"
description: "Stream agent responses in real time with Server-Sent Events."

Aegra streams agent execution to clients using Server-Sent Events (SSE). This gives you real-time token-by-token output, tool call updates, and state changes as they happen.

<Warning>
  Freebeat fork: streaming is [Agent Protocol v2](#agent-protocol-v2-event-streaming) only. The v1 run-stream endpoints (`POST /threads/{thread_id}/runs/stream`, `GET /threads/{thread_id}/runs/{run_id}/stream`, `POST /runs/stream`) answer `410 Gone`, and every run, including one created through the REST run endpoints, streams its events on `POST /threads/{thread_id}/stream/events`. See [FB_PATCHES.md](https://github.com/freebeatfit/aegra/blob/fb/0.11.0/FB_PATCHES.md) for every deviation from upstream Aegra.
</Warning>

## Quick example

```python
import asyncio
from langgraph_sdk import get_client


async def main():
    client = get_client(url="http://localhost:2026")

    async with client.threads.stream(assistant_id="agent") as thread:
        await thread.run.start(input={"messages": [{"type": "human", "content": "Hello!"}]})
        async for event in thread.subscribe(["messages", "lifecycle"]):
            print(event["method"], event["params"]["data"])
            if event["method"] == "lifecycle" and not event["params"]["namespace"]:
                if event["params"]["data"]["event"] in ("completed", "failed", "interrupted"):
                    break


asyncio.run(main())
```

The stream belongs to the thread, not the run: open it, start a run, and read the events of every run on the thread. Pick what you receive with [channels](#channels) rather than v1 `stream_mode`.

### Custom streaming

Send custom data from inside graph nodes using `get_stream_writer()`:

```python
from langgraph.config import get_stream_writer


def my_node(state):
    writer = get_stream_writer()
    writer({"progress": "Fetching data..."})
    # ... do work ...
    writer({"progress": "Processing results..."})
    return {"result": "done"}
```

Receive them on the `custom` channel (or `custom:<name>` for a named writer):

```python
async for event in thread.subscribe(["custom", "values"]):
    print(event["method"], event["params"]["data"])
```

### Subgraph events

Events of subgraphs arrive on the same stream with their `params.namespace`. Filter them per connection with `namespaces` (a prefix list) and `depth`:

```python
async for event in thread.subscribe(["messages"], namespaces=[["research"]], depth=2):
    print(event["params"]["namespace"], event["params"]["data"])
```

## REST runs

`client.runs.create`, `wait`, `join`, `get`, `cancel` and `cancel_many` still work. A run created through them executes on the same v2 event path, so an open thread stream receives its events. The v1 stream options `stream_mode`, `stream_subgraphs`, `stream_resumable` and `on_disconnect` are accepted only with their SDK defaults (see [Feature support](/feature-support)); any other value returns `422`.

### Wait for completion

If you don't need streaming but want to wait for the result:

```python
result = await client.runs.wait(
    thread_id=thread_id,
    assistant_id="agent",
    input={"messages": [{"type": "human", "content": "Hello"}]},
)
print(result)
```

This calls `POST /threads/{thread_id}/runs/wait` and returns the thread's values once the run settles, as the LangGraph Agent Server does (a run stores no output of its own).

If the run fails, the body is an error envelope instead of an output:

```json
{"__error__": {"error": "Error", "message": "KeyError: 'topic'"}}
```

`client.runs.wait()` raises on that envelope by default; pass `raise_error=False` to get it
back as a dict. The same envelope is returned when the wait gives up before the run reaches a
terminal state (`TimeoutError` or `IncompleteRun`), and by `client.runs.join()`, which returns it
rather than raising. An interrupted run is not a failure — it returns the thread's values at the interrupt.

## Keep-alive

The server sends SSE keepalive comments (`: heartbeat`) every `KEEPALIVE_INTERVAL_SECS` (default 5s, truncated to whole seconds, minimum 1s), so idle proxies (Nginx 60s, AWS ALB, Cloudflare) won't drop long-running silent agents — for example, a graph node holding an upstream WebSocket without emitting events. The wire-format matches LangGraph Platform, so existing SSE clients (the LangGraph SDK, browser `EventSource`, `httpx-sse`) silently ignore these lines per the W3C spec.

## Serialized graph values

Graph state and streamed events are converted to JSON-compatible values before
they are sent over SSE or stored in the run output. Dataclasses are serialized
recursively by field, and common Python values use these representations:

| Python value | JSON representation |
|---|---|
| `bytes` | Base64-encoded string |
| `Enum` | Serialized enum value |
| `datetime` / `date` | ISO 8601 string |
| `UUID`, `Decimal`, `Path` | String |
| `deque`, `tuple`, `set`, `frozenset` | JSON array with recursively serialized members |
| `Exception` | Object containing `type` and `message` |

Nested values inside Pydantic or LangChain model dumps are normalized using the
same rules. Mapping values are serialized recursively, and non-JSON-native keys
such as `UUID` or `Path` are converted to JSON property names with the same
scalar rules. Key collisions after conversion raise a serialization error.

## Background runs

For long-running tasks, you can create a run in the background and check on it later:

```python
# Create run (returns immediately)
run = await client.runs.create(
    thread_id=thread_id,
    assistant_id="agent",
    input={"messages": [{"type": "human", "content": "Analyze this dataset"}]},
)

# Check status
run = await client.runs.get(thread_id=thread_id, run_id=run["run_id"])
print(run["status"])  # "pending", "running", "success", "error"

# Wait for completion and get output
output = await client.runs.join(thread_id=thread_id, run_id=run["run_id"])
print(output)
```

## Cancelling runs

Cancel or interrupt a running execution:

```python
# Hard cancel
await client.runs.cancel(thread_id=thread_id, run_id=run["run_id"])

# Cooperative interrupt (if graph supports it)
await client.runs.cancel(
    thread_id=thread_id,
    run_id=run["run_id"],
    action="interrupt",
)
```

Cancellation is asynchronous while a live worker owns the run.
The cancel response may therefore still show `pending` or `running`; poll, join, or stream the run until it reaches a terminal status.
Use the REST endpoint with `wait=1` when the caller needs the request to wait briefly for the worker to settle.

### Cancelling several runs

`POST /runs/cancel` cancels many runs in one call. Select them by `thread_id` plus `run_ids`, or by status (`pending`, `running`, or `all`). The SDK exposes it as `cancel_many`:

```python
# Stop specific runs on a thread
await client.runs.cancel_many(thread_id=thread_id, run_ids=[run_a, run_b], action="interrupt")

# Stop every active run you own
await client.runs.cancel_many(status="all")
```

Runs that already finished are skipped, and only the caller's runs are affected. `action` accepts `cancel` and `interrupt`, the same values as the per-run endpoint. The response is `204 No Content`.

## SSE reconnection

Every run on a thread writes its events to one event log per thread (a Redis Stream per thread when `REDIS_BROKER_ENABLED=true`, an in-memory list in dev mode), as the LangGraph Agent Server does. Full state is the exception: the latest `values` of each namespace (the root graph and each subgraph) is kept once per thread, with its checkpoint envelope, and the log holds only a small marker where it was written. A `values` event that carries interrupts is the snapshot too, so a client that connects while the thread waits on an interrupt receives its `input.requested` from the snapshot.

A thread stream (`POST /threads/{thread_id}/stream/events`) first sends, for each requested namespace, its latest checkpoint envelope and `values`, then the log from the earliest of those snapshots on, then waits for new events with a bounded blocking read, so a run started after the stream opened, on any instance, arrives on it without polling. Each snapshot arrives at its own place in the log, and one that a newer snapshot has replaced is skipped. A reconnect therefore costs one state per namespace plus the events after it, however many steps the thread ran. If your connection drops, open the stream again: each event keeps its `event_id` and `seq`, so the SDK drops what it already has, and `since` (the last `seq` you saw) skips it on the server.

Each write trims the thread's events older than `RESUMABLE_STREAM_TTL_SECONDS`, default 120 s (the LangGraph Agent Server's name and default), but never the root snapshot's marker or the events after it, so a step longer than the window keeps everything a reconnect needs. A subgraph's snapshot goes when its marker is trimmed. A thread's keys expire one window after its last event, in both dev and production.

<Note>
  In production deployments, each open thread stream holds one connection from a dedicated Redis pool, `REDIS_STREAM_READ_MAX_CONNECTIONS` (default 2000 per instance). When the pool is full, new reads wait for a free connection instead of failing. A dropped Redis connection is reopened and the read resumes from the stream's cursor. See the [worker architecture guide](/guides/worker-architecture) for the Redis layout.
</Note>

## Agent Protocol v2 event streaming

The latest LangGraph JS and Python SDKs (including `@langchain/langgraph-sdk` and the Vue/React `useStream()` composables) speak a newer streaming protocol with a dedicated event envelope and a content-block message model. Aegra serves this protocol natively.

<Note>
  v2 streaming is **on by default** and, in this fork, the only streaming there is: the legacy `runs/stream` endpoints answer `410 Gone`. `FF_V2_EVENT_STREAMING` is a kill switch: set it to `false` to disable v2 serving (requests return `503` with an enable hint) and roll back without a redeploy. The endpoints also require a `langgraph` / `langchain-core` new enough to emit native v3 events; the server returns `503` with an upgrade hint if the runtime is too old.
</Note>

### Using the SDK

The stock LangGraph SDK drives both endpoints for you. Streaming is **thread-scoped**: open the stream, start a run, and consume the events:

```python
from langgraph_sdk import get_client

client = get_client(url="http://localhost:8000")

async with client.threads.stream(assistant_id="agent") as ts:
    await ts.run.start(input={"messages": [{"role": "user", "content": "hi"}]})
    async for event in ts.events:
        print(event["method"], event["params"]["data"])
```

The same flow backs the Vue/React `useStream()` composables.

### Endpoints

| Endpoint | Purpose |
|---|---|
| `POST /threads/{thread_id}/commands` | Run a command: `run.start` (start a run), `input.respond` (resume an interrupt). Returns a JSON response envelope. |
| `POST /threads/{thread_id}/stream/events` | Open a channel-filtered SSE stream of the thread's run events. |

The stream is scoped to the **thread**, not a run — you open it, then issue `run.start`, and the events of whatever run executes flow through. The client mints the thread id, and `run.start` creates the thread if it doesn't exist yet.

### Starting a run

```bash
curl -X POST http://localhost:8000/threads/$THREAD/commands \
  -H "Content-Type: application/json" \
  -d '{
        "id": 1,
        "method": "run.start",
        "params": {
          "assistant_id": "agent",
          "input": {"messages": [{"role": "user", "content": "hi"}]},
          "context": {"tenant_id": "acme"}
        }
      }'
# → {"type": "success", "id": 1, "result": {"run_id": "..."}}
```

`context` is forwarded to both the graph factory through `ServerRuntime[T]` and graph nodes through `Runtime[T]`. It is an Aegra extension: the Agent Protocol `run.start` params are `assistant_id`, `input`, `config`, `metadata`, and `langsmith_tracer`. For a payload that also works against LangGraph Platform, put the same values under `config.configurable`; when `context` is absent the server copies `configurable` into it.

To fork or time travel, set `config.configurable.checkpoint_id` to a checkpoint of the thread. The run replays from that checkpoint, and `input` is optional in that case. The JS SDK `forkFrom` option (the regenerate button in `useStream` and assistant-ui) sends this field. A value that is not a UUID string returns `invalid_argument`.

`langsmith_tracer` is accepted and ignored. Aegra traces through OpenTelemetry, see [Observability](/guides/observability).

Params outside the documented set are logged at warning level with their key names and otherwise ignored.

### Streaming events

The SSE filter is a POST body listing the channels you want — no run id. Pass `since` (the last `seq` you saw) to resume after a dropped connection.

The stream stays open until the client disconnects: while idle it sends a `: heartbeat` comment every 5 seconds and never closes on its own. A client that stops reading is disconnected once a send has waited 120 seconds. If the server can't read the thread's events, it sends an `error` event (`{"type":"error","error":"unknown_error",...}`) and closes the stream, so the client reconnects.

```bash
curl -N -X POST http://localhost:8000/threads/$THREAD/stream/events \
  -H "Content-Type: application/json" \
  -d '{"channels": ["messages", "values", "lifecycle"]}'
```

The client reads each frame's `data:` line — a protocol event envelope. `seq` is the cursor you echo back as `since`; it rises across runs and connections on a thread, and an event has the same `seq` on every connection. `event_id` dedups across reconnects, and a root `lifecycle` event's id names its run as `synth:<run_id>:…`. `params.data` is the payload, `params.namespace` the subgraph path, and `params.timestamp` the time the event was produced:

```
data: {"type":"event","seq":1,"event_id":"...:1","method":"messages","params":{"data":{"event":"message-start","role":"ai","id":"msg_1"},"namespace":[]}}

data: {"type":"event","seq":2,"event_id":"...:2","method":"messages","params":{"data":{"event":"content-block-delta","index":0,"delta":{"type":"text-delta","text":"Hello"}},"namespace":[]}}

data: {"type":"event","seq":3,"event_id":"...:3","method":"lifecycle","params":{"data":{"event":"completed"},"namespace":[]}}
```

### Channels

`values`, `updates`, `messages`, `tools`, `lifecycle`, `input`, `checkpoints`, `tasks`, and `custom` (plus `custom:<name>`). Message streams arrive as content-block events (`message-start` → `content-block-delta` → `message-finish`); lifecycle reports `started` / `completed` / `failed` / `interrupted`.

### Human-in-the-loop interrupts

When you subscribe to the `input` channel, a graph interrupt arrives as an `input.requested` event. Its `params.data` includes the interrupt id and two identical content fields:

```json
{
  "type": "event",
  "seq": 4,
  "event_id": "...:4",
  "method": "input.requested",
  "params": {
    "data": {
      "interrupt_id": "interrupt-id",
      "payload": {"question": "Approve?"},
      "value": {"question": "Approve?"}
    },
    "namespace": []
  }
}
```

`payload` is the Agent Protocol field consumed by the JavaScript SDK and Vue/React `useStream()` integrations. `value` mirrors it for current Python SDKs, including `ts.interrupts[].value`. If the source interrupt has no value, both content fields are omitted; explicit `null`, empty, and falsy values are preserved under both fields.

Interrupt IDs are deduplicated within each run so the same interrupt is not emitted twice when it appears in both `updates` and `values`. A resumed run may reuse an earlier run's ID; its `input.requested` event is emitted again because it belongs to a new run.

### Responding to an interrupt

`input.respond` resumes the interrupted run. Only `response` is required; `interrupt_id` targets one interrupt when several are pending.

```bash
curl -X POST http://localhost:8000/threads/$THREAD/commands   -H "Content-Type: application/json"   -d '{
        "id": 2,
        "method": "input.respond",
        "params": {
          "interrupt_id": "interrupt-id",
          "namespace": [],
          "response": {"action": "approve"},
          "update": {"reviewed_by": "alice"},
          "goto": "finalize"
        }
      }'
```

| Param | Effect |
|:--|:--|
| `response` | The value returned from `interrupt()` inside the graph. |
| `interrupt_id` | Targets one pending interrupt. Omit it only when a single interrupt is pending. |
| `responses` | Batch form: a list of `{interrupt_id, response}` entries resumed in one run. Replaces `response` and `interrupt_id`. |
| `update` | State update applied in the same superstep as the resume, as `Command(update=...)`. Must be an object. |
| `goto` | Node name, `{node}` or `{node, input}` object, or a list of those, applied as `Command(goto=...)`. `input` is optional. |
| `config`, `metadata` | Per-run overrides, same as `run.start`. |
| `context` | Aegra extension, same semantics as on `run.start`. |
| `namespace` | Accepted for protocol compatibility. Interrupt ids already encode the subgraph namespace, so the server does not read it. |

`update` and `goto` fold into the same `Command` as the resume, so the resumed run writes a single checkpoint.

  This first release covers the HTTP SSE + commands path the JS/Python SDKs use, verified end-to-end against the stock `langgraph-sdk`. The WebSocket transport and the `agent.getTree` / `state.fork` / `subscription.*` commands are not yet implemented; SSE filtering via the POST body covers the `useStream()` path without them.
</Note>
